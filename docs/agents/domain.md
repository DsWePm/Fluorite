# 领域文档与阅读顺序

Fluorite 采用单一项目上下文。文档首先服务于开发者阅读，同时为诊断、测试和架构工具提供同一份事实来源；不要维护一套只给 agent 使用、与人类文档分叉的项目知识。

## 开始工作前

1. 阅读根目录 `CONTEXT.md`，了解稳定术语、系统边界和代码入口；如果尚未建立，则继续阅读下一项，不把缺失本身当成故障。
2. 阅读 `docs/DEVELOPMENT.md` 中与当前工作相关的架构、铁律、风险和待办。
3. 阅读 `docs/adr/` 中涉及当前区域的架构决策。若实现方向与 ADR 冲突，必须明确指出并重新裁决，不能静默覆盖。
4. 根据 `docs/DEVELOPMENT.md` 的索引读取相关开发日志，了解已经结案的问题、证据和验证结果。

## 各类文档的职责

- `CONTEXT.md`：术语表、模块边界、系统地图和最短阅读入口。
- `docs/DEVELOPMENT.md`：长期有效的方法论、架构、文件说明、规则、已取得成就的摘要、危险事项和待办事项。每项已完成成就只保留一句摘要，并指向开发日志中的对应标题。
- `docs/adr/`：影响长期结构且未来修改必须重新裁决的架构决策。
- 开发日志：保存已完成里程碑、故障调查、实验数据、淘汰方案和验收过程。已经结束的过程性内容应从主开发文档迁出，而不是重复保留。

所有文档应先讲清“它是什么、为什么存在、读者接下来去哪”，再给路径、符号名和机器可执行规则。标题和术语应稳定，避免人类能理解但工具无法检索，或工具能匹配但人类无法阅读的写法。

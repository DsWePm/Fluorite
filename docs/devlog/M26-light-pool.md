## D208:预采样池实测 —— 走表就是代价,搬走它几乎全额回收

**测量**(2026-08-23,`run/rt-frame-stats/frame.csv`,10364 个真正出图的帧;`gpu.traceIndirect` 为 0 的帧全部剔除——那是菜单/加载,把它们平均进基线是第一版分析犯的错):

会话里只有**一次相邻切换**,帧 156–1107(池关)紧接帧 1108–1834(池开),中间只隔 1 帧。两侧各取中段 60% 的中位数:

| | `gpu.traceIndirect` | `gpu.lightPool` | 合计 |
| --- | --- | --- | --- |
| 池**关** | **56.62 ms** | 0 | 56.62 |
| 池**开** | **40.81 ms** | **0.029 ms** | 40.84 |
| | **−15.82 ms(比值 0.721)** | | **−15.79 ms** |

**读数可信度**:

- 平台内很紧。关档 p10–p90 = 55.7–57.9,MAD 0.54;开档 34.4–43.0,MAD 1.28。**分离量是两侧 MAD 之和的 8.7 倍。**
- 平台内漂移小:关档 +1.1%,开档 −3.5%,说明跨越边界时场景基本稳定。
- 混淆项**朝相反方向**动:`gpu.froxelBake` 0.644 → 1.028,`gpu.tlasBuild` 0.142 → 0.231。两者都变**贵**,说明开档那一侧的场景略重。所以 15.8 ms 的节省如果有偏差,是**被低估**而不是被高估。

**与 D31 对读,这才是最有说服力的部分**。D31 在 bench-water-bottom 测得发光体照亮体积的代价是 **+20.9 ms**(59.707 开 / 38.812 关)。这次是 **56.62 → 40.81**,而 40.81 几乎正落在 D31「只有散射顶点、没有发光体 NEE」的 38.8 上。

也就是说:**池把发光体 NEE 的开销几乎全额回收了。** 两次独立测量、不同场景、相隔很久,却指向同一个结论 —— D31 当年判定「代价是那条依赖链而不是阴影线」是对的,而把链搬出采样点就把它拿掉了。

**池自己只要 0.029 ms**。它随「有光源的格数 × 深度」增长,这个存档的光源密度不高;光源密集的场景会更贵,但基数是每格每帧一次而不是每样本一次,量级不会翻身。

**这次测量的欠缺,必须写下来**:

1. **只有一次切换,没有回归平台。** 铁律 7 要求 A→B→A、第三个平台回到第一个,以证明读数不是漂移。这个文件里做不到——后面两个开档平台(62.5 ms 和 19.5 ms)之间没有关档,是不同场景,不能拿来对比。
2. **位姿未经确认固定。** 漂移和混淆检查都支持"跨边界时场景稳定",但那是推断,不是记录。
3. **CSV 无法确认「发光体照亮体积」在两侧都开着。** 池的开关和发光体 NEE 的开关都不写进 frame-stats。逻辑上它必然是开的——关掉的话雾就不被照亮了,而这次是**通过了画面验收**才来看性能的;但这一条靠的是使用者的陈述,不是文件。

结论按测量到的强度成立,按上面三条打折。**要把它当成定论,需要一次带回归平台的固定位姿复测。**

**对切片二的意义**:表面着色走的是同一条依赖链,`lighting.slang` 记为 18 ms 帧里的 5.9 ms。这次的结果把「池能不能救那 5.9 ms」从推测变成了有先例的推断——但仍然是推断,切片二落地后要自己测自己的。

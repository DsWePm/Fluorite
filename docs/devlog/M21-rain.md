# M21：雨天表面系统

M21 在 2026-08-14 完成功能视觉验收。它把降雨从固定亮度的光栅装饰扩展为世界锚定、可遮挡、具有连续湿润历史并与路径追踪材质和统一光源接口相连的系统。长期架构、ABI 和回归标准仍以 [`docs/DEVELOPMENT.md`](../DEVELOPMENT.md) 为准；本文保留 D105–D129 的结案摘要。

## 最终成果

- 沿全局雨向维护 256²/512² 世界空间暴露深度图，以 32² tile 近场优先、远场渐进更新；每帧最多 8192 条 RayQuery。地图重定位会清除未解析区域，CPU 群系降水缓存也采用滑动复用和渐进补齐。
- GPU 双缓冲湿润历史为每条雨线保存当前/前一层表面的深度、水膜和积水量，使遮挡出现或移除后按浸湿、干燥、填充和蒸发时间连续变化。普通方块和树叶只处理几何顶面，小型透雨植物允许各可见面湿润且不遮住下方地面。
- format-3 材质可声明吸水、变暗、水膜保持和蓄水能力。湿表面以水 IOR 1.333 的分层 GGX 薄膜处理；水坑是世界锚定 FBM 场，并与水膜共享湿润颜色端点及连续法线过渡。原生水、玻璃和粒子不会误取方块水膜。
- 原生水面和水坑共享无状态、世界锚定的随机雨滴冲击事件。RT 水花由 CPU 从同一事件定义选择稀疏子集，使用 Fluorite 自有中性水冠/水滴模型并复用粒子 BLAS，不再与原版蓝色水滴重复。
- 密集雨丝在 DLSS-RR 之后、曝光之前进入 HDR pass。D129A 由 compute 每实例计算一次直接光，天空、天体和统一 `Light`/alias/grid 局部光源共同决定颜色与亮度；天体和局部光各最多一条不透明阴影线，并删除夜间固定白色亮度下限。

## 关键裁决与边界

- 否决全图逐帧追踪和纯 CPU 湿润历史：前者 RayQuery 成本过高，后者需要持续读回/上传且不适合逐像素并行更新。最终采用 GPU 分层历史与渐进暴露缓存。
- 水坑不使用真实几何或视差，也不限制固定面积；当前薄层模型优先保证路径一致性和稳定成本，不模拟毫米级水体的真实自由表面位移。
- 涟漪采用阻尼波列的解析近似，没有复制外部 shader 代码，也没有反馈浅水求解，因此不承诺波纹碰撞和相互干涉。
- 水花当前只进入主摄像机路径与可选阴影，不进入反射/GI；雨丝是单次散射近似，不模拟球形水滴高频焦散。~~M21 不实现雪。~~ **雪已于 D177 实现，见下节**；水花与湿润仍然只属于雨。
- Debug View 26/27 与视觉校准旋钮保留为 ReSTIR 前 review 候选；它们不是长期配置 ABI。是否固化数值并删除，必须在专项 review 后由用户确认。

## 验收与验证

开发期间依次验收了顶面/植物湿润资格、非方块化干湿边界、水坑可见性与颜色连续性、涟漪和水花共享事件、雨丝方向一致性，以及 D129A 的昼夜/局部光照响应。最终功能视觉验收于 2026-08-14 通过。

## D177：实现雪（用户指示，2026-08-15）

### 起因是一次误报，而误报本身是对的

用户报「新建的世界里 `/weather rain` 不下雨，回到别的世界就有」。查下来 **恶地是 `Precipitation.NONE`，不下雨是正确行为**。但排查过程暴露了真正的缺口：分类只有 `RAIN` 和 `NONE` 两类，**`SNOW` 被归进了 `NONE`**——于是雪原、雪山、以及任何普通群系的高海拔处，暴露烘焙都会写下 `-1`（「这里什么都不落」），而 `rain_streak.vert` 对 `depth < 0` 一律剔除。**下雪的天气渲染成一片空无。**

顺带记下这条容易被忽略的放大因素：降水查询用的是 `MOTION_BLOCKING` 地表高度，而 MC 的群系温度随高度下降——**同一个群系，海平面下雨、山上下雪**。这既是缺口的放大器，也是修好之后「山腰有雪线」这一效果的来源，两者是同一件事。

### 三条裁决（用户选定）

| 项 | 选定 | 未选的代价 |
|---|---|---|
| 范围 | **只做飘雪** | 地面变白由 MC 自己的雪层方块提供，渲染器再做一遍会叠加。代价是墙面、玻璃、树叶下缘这些放不下雪层方块的地方仍然完全不变 |
| 飘法 | **curl 噪声** | 每片自己的正弦摆动几乎免费，但一片雪花在视野里存在二十秒，各自独立摆动会读成「一堆各自抽搐的白点」 |
| 设置 | **雪速 + 雪花尺寸两个新项** | 雪速无法与雨共用：雨默认 24 格/秒，是雪花终端速度的约二十倍 |

### 雪不能复用长条几何，这是算术不是审美

雨的 streak **就是运动模糊**：24 格/秒下一帧走 0.4 格，所以 0.7 格的长条是对的。雪按裁决后的默认 2.4 格/秒，一帧走 **0.04 格** —— 没有模糊可画，拉长只会渲染出物理上不存在的拖影。所以雪是**朝向相机的小方片 + 圆形衰减**，而雨那条路径**一个字节都没动**。

连带后果：48 格下落跨度、2.4 格/秒 → 一片雪花在视野里存在 **20 秒**。这正是「飘法」权重高的原因，也是选 curl 而非正弦的理由。

### curl 解析求值，不绑纹理

D173 烘了一张 32³ curl 体，但那是为了避免在 march 里**每步重算六次 Perlin**。这里每片雪花每帧只求一次、最多一万六千次——**把 3D 纹理绑到另外两条管线（streak 的 light compute 与 vertex）在描述符、管线布局和出错机会上都比这点 ALU 贵**。所以直接调 `cloud_field.curlNoise`，那个模块本来就是无绑定的。

curl 而非任意噪声向量场，理由与 `cloud_warp.comp.slang` 横幅相同：任意场有源有汇，按它平移会把雪花**挤成团**；curl 处处无散度，只剪切不压缩。

**场是世界锚定且静态的**，这一条才是「读起来像雪」的关键：相邻雪花采到几乎相同的向量，于是**成片一起旋**——那正是一阵风的样子。飘动本身来自雪花**穿过**这个静止场的下落，因此不需要任何逐雪花状态（这些无状态程序化实例也存不下状态）；场再以极慢的速度顺风漂移，免得像钉在世界上。

### 位置改由 light compute 独占计算

原先 vertex 与 light compute **各自调用同一个 `rainStreakPlacement`**，注释写着「shared verbatim」。雨可以这样：位置是相位的闭式解。**雪不行**——它需要该列的降水分类（一次缓冲读取）再加一次 curl 求值。与其两边各算一遍然后指望它们一致，不如 **compute 算一次、写进 per-instance 缓冲，vertex 读它**。约定因此变成了结构事实。

一个必须注意的顺序细节：位置要写在**视锥剔除的提前返回之前**。那个 early-out 原本只影响 radiance（写不写都是 0），但位置一旦漏写，vertex 读到的就是上一帧的位置。

### 最大的回归风险：让雪拿到深度，等于把整台湿润机器指向它

这是本轮唯一真正危险的地方，值得写清楚。修好雪的做法是让 `SNOW` 列**和雨一样拿到真实的暴露深度**（屋檐挡雪和挡雨是同一件事，同一条射线）。但湿润链路把「有深度」直接当成「正在被淋湿」——所以同一个修复会让**暴风雪灌满水坑**。它不崩溃、不报警，只是看起来像下雨。

分类因此必须抵达三处，而它们分属三条管线、无法共享描述符集：

| 消费者 | 路由 | 作用 |
|---|---|---|
| `rain_surface.slang` | `pc.rainPrecipitationAddr`（新增第 13 个地址） | 着色期湿润的**唯一漏斗**，文件内每个湿润查询都经过它 |
| `rain_history.comp` | 自有 push 新增地址 | 保留式湿润水库，漏斗覆盖不到 |
| streak 两阶段 | `RainStreakPush` 新增地址 | 决定形状、速度与散射响应 |

解码集中在新的无绑定模块 `precipitation.slang`，理由与 `cloud_density.slang` 相同：**四个消费者、三条管线、一份实现**。`precipitationWets()` 只对 `PRECIP_RAIN` 返回真，是这条不变量的唯一落点。

`rain_history` 的写法值得一提：不是在下游加分支，而是**把雪的深度改写回「什么都不落」的 −1**，于是干燥、层匹配、屋顶变化处理全都继续只看见一种情况。

### push constant 余量已经见底

`WorldPushConstants` 从 112 B 涨到 **120 B**，而 Vulkan 保证的下限是 128 B。原来的测试注释留了一句「下一个加地址的人应当重算这段算术，而不是信这条注释」——照做了：**现在只剩 8 B**。再加一个地址会精确顶到 128（14×8+12=124→128），一个字节不剩；**再下一个在只提供最小值的硬件上放不下，而 AMD 恰好只给最小值**。第十四个地址应当考虑改放进 `WorldPush`（BDA 结构，无此上限，代价是一次解引用）。这段已写进测试。

### 已知近似

- 雪花的 curl 偏移**在**分类之后施加，而遮挡测试用的是偏移后的位置。于是一片被吹出 1.8 格的雪花，可能按 A 列分类却被 B 列的屋顶遮挡。4 格的粗格下这偶尔会跨格；物理上说得过去（被吹到屋檐下的雪本就该被挡住），故不做处理。
- 雪的散射响应取雨的 3.5 倍，**是拟合不是推导**——与雨那个 0.004×4π 的性质相同，注释里照此说明。
- 雪不产生水花（`RtRainImpacts` 本就只认 `RAIN`），不产生湿润，不在反射/GI 中出现（与雨丝相同）。

### 验证状态

Java 与 shader 全量编译通过，Fabric **153** 项测试通过（新增 2 项）。新契约钉的正是上面那条回归：`PRECIP_SNOW` 在 Slang 与 Java 两侧都存在、烘焙按 `precipitationFalls` 分流、而**三个湿润入口各自都在测 `precipitationWets`**；以及「雪不画成长条」的几何与 curl 的空间相关性。

顺带发现一处既有缺口（非本轮引入）：**`zh_tw.json` 只有 393 条，`en_us`/`zh_cn` 各 667 条**——整个雨天粒子小节在繁中缺失。本轮的两条新文案已按三语补齐，但那 274 条的缺口仍在。

### 游戏内第一次验收：有雪，但是黑的

用户确认雪出现了，但**渲染成黑色**。原因不是「亮度调低了」，是一个符号错误级别的问题：

streak 走的是**直通 alpha over** 混合，所以一个片元贡献的是 `alpha × (L_粒子 − L_背景)`。**当粒子比它背后的东西暗，画它就是在减光。** 雪按当时的响应只有天空辐亮度的约五分之一，却以 0.55 的 alpha 盖住整个像素——阴天下的雪于是成了黑点。雨一直躲过同一套算术，只因为它的线是发丝宽的、alpha 也更低。

**修法不是调常数，是换模型。** 雨滴是透明的：它把大部分光折射着送走，只朝观察者散一点，那个拟合出来的小数字是对的。雪花是反面——不透明、近乎纯白的冰晶聚合体，正确的模型是**小的漫射粒子**：

> 各向同性辐亮度 L 浸浴下的朗伯粒子，辐照度为 πL，出射辐亮度 = albedo·(πL)/π = **albedo·L**。

而这里的 `source` 恰好已经就是那个平均入射辐亮度：`mediumSkyRadiance` 本身是 1/(4π) 球面积分，太阳项以 `E/(4π)` 进入——**而 E/(4π) 正是漫射球面在其表面上的平均**（截面 πr² 除以面积 4πr²）。所以源的组装一个字不用改，**响应就是反照率**。新雪的宽带反照率 0.8–0.9，取 **0.9**。这是推导，不是上一版那个 3.5× 的拟合。

### 顺带修掉一个雨也有的缺陷

light compute 会对自己视锥外的实例提前返回，radiance 停在清零值。在 alpha over 下**零不等于隐形，等于减光**。所幸信号本来就存在：该 pass 对真正着色过的实例写 `w = 1`。vertex 现在读整个 float4 并在 `lit.w <= 0` 时剔除。**这条对雨同样成立**，只是黑边雨丝比黑雪花难注意。

### 设置分栏与旋钮改名（用户指出）

用户指出雨的粒子数旋钮同时控制雪，要求分栏并消除歧义。审计结果——**同时控制雨与雪的共有五项**：

| 旧名 | 实际作用范围 | 新名 |
|---|---|---|
| Rain Streaks and Splashes | 整个 streak pass，雨雪都关 | **降水粒子** |
| Rain Streak Budget | 实例上限，雨雪共用 | **降水粒子预算** |
| Rain Streak Density | 实际用量，雨雪共用 | **降水粒子密度** |
| Rain Slant | 下落方向，且是遮蔽图追踪的方向 | **降水倾角** |
| Exposure Map | 遮蔽图分辨率，挡雪与挡雨是同一件事 | **降水遮蔽图** |

天气页由一栏拆成三栏：**降水粒子（雨与雪共用）／仅雨／仅雪**。

**只改显示名与分栏，配置键一律未动**——键名改动会让已有配置文件失效，而歧义在 UI 上，不在存档里。Java 标识符仍是 `RAIN_*`，这一点记在此处以免下次被当成疏漏。

**尚未裁决**：密度是否应当拆成雨、雪各一个。当前共用意味着调稀雨的同时调稀了雪。用户本轮只要求改名，故未擅自拆分。

### 本轮同时立的两个 issue

- [#40](https://github.com/DsWePm/Fluorite/issues/40) 近相机降水粒子拉出斜线。`rain_streak.vert.slang` 里的 `nearCamera` 注释描述的正是这类故障，说明机制已知而防御不足：它收缩长度但从不收缩宽度，且是渐隐而非硬剔除。
- [#41](https://github.com/DsWePm/Fluorite/issues/41) 矿洞远处雾被无遮挡天空照亮。**用户判断的症状与不对称都成立，但机制不是「某一套没写遮挡」**——三条环境路径都乘了 `visibilityGrid` 的 sky 项；差别在于**采样点是否落在网格内**：网格默认 64×32×64 格（约水平 ±32 格、垂直 ±16 格），出界即返回「完全开阔」，且在距离面 6% 处就开始朝「开阔」渐隐。水下之所以正确，是因为它在水面上方取样，那个点通常牢牢在网格内。「两套叠加」一节则**未证实**，两者按设计覆盖不相交的 segment，须先用 `volumetrics.segment-source` 隔离开关验证。

**游戏内仍需验证**：雪是否已是白的、雪是否成片一起旋、屋檐下是否没有雪、以及**雪地里地面不会变湿变亮**（最后一条仍是本轮最大的回归风险点）。

## 起点：ReSTIR 的前一半已经在了

开工前的实测：`lighting.slang` 已有 `Reservoir` 结构和 `risInitial` —— **每着色顶点一次 RIS**，M 个功率加权候选（默认 8，六本地二全局）、alias O(1) 选择、幸存者一条阴影线。`world.rgen.slang:660` 的注释自己写着「single-frame only, no temporal reservoir reuse」。

**缺的是 reuse。** 本里程碑要补的正是时间与空间复用，而复用需要**每像素持久的 reservoir 存储**——这是完全没有的东西。

## D180：先做未压缩版，把「值不值」变成可测量

三个方向性问题请示用户，三个都选了比推荐更贵的档：

| 问题 | 我的推荐 | 用户裁定 |
| --- | --- | --- |
| §8.9「不要提前做时空复用」怎么读 | 依赖满足后可做 | **同上** |
| reservoir 怎么存 | 压缩 ~12 B | **全量** |
| 复用覆盖哪些顶点 | 只主命中 | **全弹射** |

后两项叠加后的内存我在选项里没给全（选项里的 232 MB 是只主命中的），补算后是 1080p/4 弹射约 1 GB。用户的裁定是：

> 你先实现 A 然后 A 要是爆显存了我们再走 C 这样合理一点吧，不实验怎么知道值不值呢

**这与铁律 7 一致**（性能结论只认实测），因此照办。据此产生两条设计约束：

1. **存储格式必须关在一个可替换的边界后面。** `restir.slang` 的 `packReservoir` / `unpackReservoir` / `reservoirSlot` 三个函数 + 一个尺寸常量就是全部接口。改走压缩档时改这四处，不动任何调用点。
2. **存储要先于复用逻辑落地。** 缓冲分配本身就能回答「A 会不会爆显存」，不必等任何复用代码写出来。已验证：用户在深度 4 下分配成功。

### 64 B 而不是 56 B

字段加起来是 56，但 std430 给纯标量成员的结构 stride 就是 56——**不是 16 的倍数**，于是这个「每像素每弹射顶点读一次」的缓冲上每隔一个元素跨 cache line。改成四个 `float4`，多付 14% 换永不跨行。

实际占用 `2 (双缓冲) × 64 B × 复用深度 × 渲染像素`：1080p 下**每层深度 265 MB**，默认弹射数 4 约 1 GB，配置上限 8 约 2 GB。

### 关档与旋钮

`composite.restir-reuse-depth` 默认 **0** = 关：不分配缓冲、push constant 地址为 0、着色回落到单帧 RIS，**与本缓冲存在之前字节级一致**（铁律 8）。旋钮在 Tracing 栏而非诊断栏，因为它改变渲染器行为而不是观测它。

### 这一步消耗了最后一个 push constant 地址

`WorldPushConstants` 现为 14 个地址 + 3 个 uint = 124 → 128 B，**正好是 Vulkan 保证的下限，也正好是 AMD 提供的量**。`RtMaterialLayoutTest` 在还剩 13 个地址时就预言了这个算术并指明了下一步；现在它记录的是「没有余量了，第 15 个地址必须放进 `WorldPush`」——那是 BDA 结构、无此上限，代价是一次间接寻址。

**判据**：新地址是否该放这里，取决于 closest-hit 是否需要它（hit shader 每次命中都读 `pc`、故意从不碰 `WorldPush`）。除此之外现在一律是否。

### 一个自己引入又自己修掉的 bug

`ensureOutput` 在窗口与 upscaler 未变时提前返回。它此前守的一切都只随这两者变化，所以条件里没有 reservoir 深度——**旋钮要等到下一次分辨率变化才生效**。

一个延迟一次 resize 才生效的开关比不存在更糟：它存在的意义就是 A/B，而这样的 A/B 会拿同一棵树跟自己比，然后报告「没差别」。

## D181：接收顶点存世界坐标，因为弹射顶点没有深度

第一版存的是「相机射线深度 + 法线」。**对主命中完全够用，往里走一次弹射就毫无意义**：弹射顶点上没有相机射线，而槽位按 `(像素, 弹射序号)` 寻址、**没有任何重投影**，所以上一帧该像素的第 3 次弹射可以在世界任何地方。

用深度比对等于拿两个不相干的数在比，**碰巧接近就接受** —— 那会是「看起来在工作」的时间复用，实际把上一帧的光照贴到不同几何上。

改存接收顶点的**世界坐标**。腾出的 lane 来自删掉 `wSum` 与 `phat`：

- `phat` **必须**在复用它的那个顶点上重算。把产生它的顶点的值带过来，正是让时间复用出错的经典错误。
- `wSum` 只在 reservoir 填充期存在。
- `W` 才是成品权重，也是着色唯一消费的量。

`unpackReservoir` 对这两个返回 0 而不是看着合理的陈值——读它们而不重算的调用方会立刻得到显然错误的答案，而不是一个似是而非的。

**这条修改发生在任何代码读该格式之前**，是它最便宜的时刻，也正是 D180 把格式关进三个函数的目的。

### 复用判据

两组独立检查，都必须通过：

- **接收端**：位置漂移 ≤ 0.05 格、法线夹角 ≤ 26°。没有重投影，这是复用与「把上一帧光照贴到无关几何上」之间唯一的东西。
- **光源端**（§8.9 硬性要求）：位置、半径（矩形面积）、Radiance **三项全查**。30 bit source key 只标识候选身份，而 entity id 与哈希**都会复用**——只查 key 会静默替换成另一个光源。

**阈值故意放松**：幸存者反正要在当前顶点重算目标函数，所以边缘接受只损失一点精度（且由 S2 的 MIS 权重兜底），边缘拒绝损失的是整个特性。这里错向「接受」更便宜。

`REUSE_M_CAP = 20`（历史上限）沿用文献起点，其定价属 §8.11 测量欠账。

## D182：接上复用时才发现的三件事，三件都请示后定案

存储层写完、真要把它接进 `world.rgen.slang` 时，读代码读出三个当初列选项时没看见的问题。全部带分析请示，用户三选。

### A：一个像素每帧调 `tracePath` `spp × MAX_PATH_SEGMENTS` 次，它们会撞同一个槽

`main()` 的双层循环里每次调用都**从 `seg.bounce` 重新起算自己的弹射编号**。槽位只按 (像素, 弹射) 寻址的话，它们全部落在同一个格子上：最后写的赢，而**第一个之后的每个样本读到的都是另一个样本刚写下去的东西**。

这不是崩溃也不是黑屏——是一份看起来正在工作的时间复用，实际在合并互不相干的历史。spp 个样本共享一份历史会让它们的噪声相关（吃掉 spp 平均的收益）；第二个 leaf 是折射分支、**是另一个表面**，拿主路径的接收端去校验它毫无意义。

| 选项 | 显存（1080p / 深度 4 / spp 1） | 代价 |
| --- | --- | --- |
| 只 leaf0+sample0 参与 | 1.06 GB | 折射分支永不复用；spp>1 时只有 1/spp 受益 |
| 全参与、最后写的赢 | 1.06 GB | 噪声相关；折射分支白付一次读 |
| **槽位按路径分档**（用户选） | **2.12 GB** | 每条路径有自己的历史，无相关无覆写 |

用户选了最贵的一档，与 D180 的实验精神一致。落地为 `reservoirSlot` 的 `pathIndex/pathCount` 维度，`pathIndex` 直接复用 `tracePath` 已有的 `sampleIndex`（`s + leaf * spp`）——两处用的是同一个数，因为它们问的是同一件事：这是该像素的第几条路径。

**槽位按 `hitDepth` 而非 `bounce`。** `bounce` 从 pass A 留下的位置起算，在折射分支上可能不是 0，会让 0 号槽空着并越过深度上限；`hitDepth` 在两条分支上都从 0 数**着色顶点**，而 reservoir 正是每着色顶点一个。

### B：光源侧校验当时是写在注释里的，代码没做

第一版 `reservoirReusable` 的注释宣称按 §8.9 查了位置、半径、Radiance 三项，实际只查了 `area > 0`、`W > 0` 和 NaN——**它在拿存下的样本跟它自己比**。

后果不是噪声而是幽灵：火把被挖掉后，存下的样本仍带着位置、Radiance、面积，目标函数重算出同样的值，阴影线穿过火把原来所在的空气、无遮挡，**而且每帧又被写回去，所以它不会衰减**。够亮够近的幽灵会一直赢。

三个选项里用户选了现在堵：`misc.z` 存光源索引，复用时重读那条 32 B `Light` 记录。索引就是 §8.9 说的 source key，并且是按那条注记要求的方式用的——**用它找到候选，绝不用它接受候选**。光源索引每帧从地形层级重建，所以某个区块一变，索引 N 就是另一盏灯，这正是 entity id 复用的同一类情形，靠三项比对抓：

- **Radiance**、**面积**：说明「是同一种灯」；
- **存下的采样点是否仍落在该矩形内**：三项里唯一一项**移动过的灯过不去**的，而实体光每帧都在移动。

失效方向是安全的：随便放一个火把就会让它之后所有索引平移、当帧大面积拒绝复用，下一帧存的就是新索引，自愈。地形 rebase 对接收端检查是同样的一帧代价。

### C：`RtRestirStats` —— 配置文档点了名，但类还不存在

`RESTIR_REUSE_DEPTH` 的 javadoc 早就写着「RtRestirStats 报告每层深度的接受率」。这是回答「深层值不值 530 MB」的唯一依据，落地为 host-visible 计数缓冲。

- **计数不是标志位。** 一个像素的每条路径在每层深度上独立发问且经常给出不同答案，按位 OR 会让「任何一条路径接受」就记成整像素接受，报出来的率偏乐观——而那正是这一层深度被审判的那个数。用每深度一个 nibble 计数、饱和在 15。
- **抽样 1/16，随帧轮转。** 比值在抽样下无偏（分子分母同一批像素），代价从两百万次原子加降到十几万次。
- **不用 subgroup 归约。** 光追 stage 不保证在 `subgroupSupportedStages` 里；一个在某些驱动上编不过的诊断，比多发十六次原子加更糟。
- **某层深度「没有任何路径到达」不计作拒绝**，否则深层会因为一个完全无关的原因（根本没走那么深）被报成没用。

### 顺带堵掉的一个 32 位坑

`reservoirSlot` 返回 `uint`，反汇编生成的 SPIR-V 确认 `OpPtrAccessChain` 的 Element 就是 32 位。驱动是否在乘 64 B 步长前先扩宽，规范没有钉死。所以把 store 钉在 4 GiB 以下，让这个问题不可能发生——1080p / spp 1 恰好在顶格（深度 8 = 3.96 GiB）能塞下，1440p 或 spp 2 塞不下，两者都是设置界面里点得到的配置。超了就削深度并打日志。

**削减值必须参与 `ensureOutput` 的提前返回判定，而不是原始请求值**。否则条件永远不满足，那个最大 4 GB 的缓冲会每帧释放重建、每次还带一次 `waitIdle`——表现为帧率塌方而画面一个像素都不错。这是 D180 里那个「设置晚一次 resize 才生效」bug 的镜像版本。

### S1 是有偏的，而且知道偏在哪

存下的 reservoir 的 M 个候选是在**上一帧的顶点**上抽的，把它们当作这一帧这个顶点的候选来计数，就是不带 MIS 权重的朴素 ReSTIR 合并。两个顶点对光源看法不同的地方（轮廓、掠射角、26° 法线窗口放进来的一切）M 增长而权重没有，结果偏暗。接收端检查是让它保持小的东西，**S2 的 MIS 权重才是消除它的东西**。

故意没有加「存下的样本在这里没贡献就不计 M」这种补丁：它会把偏暗藏起来，换成一个讲不出道理的偏亮，还会让 S2 更难干净地替换掉这一项。

## 起点：ReSTIR 的前一半已经在了

开工前的实测：`lighting.slang` 已有 `Reservoir` 结构和 `risInitial` —— **每着色顶点一次 RIS**，M 个功率加权候选（默认 8，六本地二全局）、alias O(1) 选择、幸存者一条阴影线。`world.rgen.slang:660` 的注释自己写着「single-frame only, no temporal reservoir reuse」。

**缺的是 reuse。** 本里程碑要补的正是时间与空间复用，而复用需要**每像素持久的 reservoir 存储**——这是完全没有的东西。

## D180：先做未压缩版，把「值不值」变成可测量

三个方向性问题请示用户，三个都选了比推荐更贵的档：

| 问题 | 我的推荐 | 用户裁定 |
| --- | --- | --- |
| §8.9「不要提前做时空复用」怎么读 | 依赖满足后可做 | **同上** |
| reservoir 怎么存 | 压缩 ~12 B | **全量** |
| 复用覆盖哪些顶点 | 只主命中 | **全弹射** |

后两项叠加后的内存我在选项里没给全（选项里的 232 MB 是只主命中的），补算后是 1080p/4 弹射约 1 GB。用户的裁定是：

> 你先实现 A 然后 A 要是爆显存了我们再走 C 这样合理一点吧，不实验怎么知道值不值呢

**这与铁律 7 一致**（性能结论只认实测），因此照办。据此产生两条设计约束：

1. **存储格式必须关在一个可替换的边界后面。** `restir.slang` 的 `packReservoir` / `unpackReservoir` / `reservoirSlot` 三个函数 + 一个尺寸常量就是全部接口。改走压缩档时改这四处，不动任何调用点。
2. **存储要先于复用逻辑落地。** 缓冲分配本身就能回答「A 会不会爆显存」，不必等任何复用代码写出来。已验证：用户在深度 4 下分配成功。

### 64 B 而不是 56 B

字段加起来是 56，但 std430 给纯标量成员的结构 stride 就是 56——**不是 16 的倍数**，于是这个「每像素每弹射顶点读一次」的缓冲上每隔一个元素跨 cache line。改成四个 `float4`，多付 14% 换永不跨行。

实际占用 `2 (双缓冲) × 64 B × 复用深度 × 渲染像素`：1080p 下**每层深度 265 MB**，默认弹射数 4 约 1 GB，配置上限 8 约 2 GB。

### 关档与旋钮

`composite.restir-reuse-depth` 默认 **0** = 关：不分配缓冲、push constant 地址为 0、着色回落到单帧 RIS，**与本缓冲存在之前字节级一致**（铁律 8）。旋钮在 Tracing 栏而非诊断栏，因为它改变渲染器行为而不是观测它。

### 这一步消耗了最后一个 push constant 地址

`WorldPushConstants` 现为 14 个地址 + 3 个 uint = 124 → 128 B，**正好是 Vulkan 保证的下限，也正好是 AMD 提供的量**。`RtMaterialLayoutTest` 在还剩 13 个地址时就预言了这个算术并指明了下一步；现在它记录的是「没有余量了，第 15 个地址必须放进 `WorldPush`」——那是 BDA 结构、无此上限，代价是一次间接寻址。

**判据**：新地址是否该放这里，取决于 closest-hit 是否需要它（hit shader 每次命中都读 `pc`、故意从不碰 `WorldPush`）。除此之外现在一律是否。

### 一个自己引入又自己修掉的 bug

`ensureOutput` 在窗口与 upscaler 未变时提前返回。它此前守的一切都只随这两者变化，所以条件里没有 reservoir 深度——**旋钮要等到下一次分辨率变化才生效**。

一个延迟一次 resize 才生效的开关比不存在更糟：它存在的意义就是 A/B，而这样的 A/B 会拿同一棵树跟自己比，然后报告「没差别」。

## D181：接收顶点存世界坐标，因为弹射顶点没有深度

第一版存的是「相机射线深度 + 法线」。**对主命中完全够用，往里走一次弹射就毫无意义**：弹射顶点上没有相机射线，而槽位按 `(像素, 弹射序号)` 寻址、**没有任何重投影**，所以上一帧该像素的第 3 次弹射可以在世界任何地方。

用深度比对等于拿两个不相干的数在比，**碰巧接近就接受** —— 那会是「看起来在工作」的时间复用，实际把上一帧的光照贴到不同几何上。

改存接收顶点的**世界坐标**。腾出的 lane 来自删掉 `wSum` 与 `phat`：

- `phat` **必须**在复用它的那个顶点上重算。把产生它的顶点的值带过来，正是让时间复用出错的经典错误。
- `wSum` 只在 reservoir 填充期存在。
- `W` 才是成品权重，也是着色唯一消费的量。

`unpackReservoir` 对这两个返回 0 而不是看着合理的陈值——读它们而不重算的调用方会立刻得到显然错误的答案，而不是一个似是而非的。

**这条修改发生在任何代码读该格式之前**，是它最便宜的时刻，也正是 D180 把格式关进三个函数的目的。

### 复用判据

两组独立检查，都必须通过：

- **接收端**：位置漂移 ≤ 0.05 格、法线夹角 ≤ 26°。没有重投影，这是复用与「把上一帧光照贴到无关几何上」之间唯一的东西。
- **光源端**（§8.9 硬性要求）：位置、半径（矩形面积）、Radiance **三项全查**。30 bit source key 只标识候选身份，而 entity id 与哈希**都会复用**——只查 key 会静默替换成另一个光源。

**阈值故意放松**：幸存者反正要在当前顶点重算目标函数，所以边缘接受只损失一点精度（且由 S2 的 MIS 权重兜底），边缘拒绝损失的是整个特性。这里错向「接受」更便宜。

`REUSE_M_CAP = 20`（历史上限）沿用文献起点，其定价属 §8.11 测量欠账。

## D182：接上复用时才发现的三件事，三件都请示后定案

存储层写完、真要把它接进 `world.rgen.slang` 时，读代码读出三个当初列选项时没看见的问题。全部带分析请示，用户三选。

### A：一个像素每帧调 `tracePath` `spp × MAX_PATH_SEGMENTS` 次，它们会撞同一个槽

`main()` 的双层循环里每次调用都**从 `seg.bounce` 重新起算自己的弹射编号**。槽位只按 (像素, 弹射) 寻址的话，它们全部落在同一个格子上：最后写的赢，而**第一个之后的每个样本读到的都是另一个样本刚写下去的东西**。

这不是崩溃也不是黑屏——是一份看起来正在工作的时间复用，实际在合并互不相干的历史。spp 个样本共享一份历史会让它们的噪声相关（吃掉 spp 平均的收益）；第二个 leaf 是折射分支、**是另一个表面**，拿主路径的接收端去校验它毫无意义。

| 选项 | 显存（1080p / 深度 4 / spp 1） | 代价 |
| --- | --- | --- |
| 只 leaf0+sample0 参与 | 1.06 GB | 折射分支永不复用；spp>1 时只有 1/spp 受益 |
| 全参与、最后写的赢 | 1.06 GB | 噪声相关；折射分支白付一次读 |
| **槽位按路径分档**（用户选） | **2.12 GB** | 每条路径有自己的历史，无相关无覆写 |

用户选了最贵的一档，与 D180 的实验精神一致。落地为 `reservoirSlot` 的 `pathIndex/pathCount` 维度，`pathIndex` 直接复用 `tracePath` 已有的 `sampleIndex`（`s + leaf * spp`）——两处用的是同一个数，因为它们问的是同一件事：这是该像素的第几条路径。

**槽位按 `hitDepth` 而非 `bounce`。** `bounce` 从 pass A 留下的位置起算，在折射分支上可能不是 0，会让 0 号槽空着并越过深度上限；`hitDepth` 在两条分支上都从 0 数**着色顶点**，而 reservoir 正是每着色顶点一个。

### B：光源侧校验当时是写在注释里的，代码没做

第一版 `reservoirReusable` 的注释宣称按 §8.9 查了位置、半径、Radiance 三项，实际只查了 `area > 0`、`W > 0` 和 NaN——**它在拿存下的样本跟它自己比**。

后果不是噪声而是幽灵：火把被挖掉后，存下的样本仍带着位置、Radiance、面积，目标函数重算出同样的值，阴影线穿过火把原来所在的空气、无遮挡，**而且每帧又被写回去，所以它不会衰减**。够亮够近的幽灵会一直赢。

三个选项里用户选了现在堵：`misc.z` 存光源索引，复用时重读那条 32 B `Light` 记录。索引就是 §8.9 说的 source key，并且是按那条注记要求的方式用的——**用它找到候选，绝不用它接受候选**。光源索引每帧从地形层级重建，所以某个区块一变，索引 N 就是另一盏灯，这正是 entity id 复用的同一类情形，靠三项比对抓：

- **Radiance**、**面积**：说明「是同一种灯」；
- **存下的采样点是否仍落在该矩形内**：三项里唯一一项**移动过的灯过不去**的，而实体光每帧都在移动。

失效方向是安全的：随便放一个火把就会让它之后所有索引平移、当帧大面积拒绝复用，下一帧存的就是新索引，自愈。地形 rebase 对接收端检查是同样的一帧代价。

### C：`RtRestirStats` —— 配置文档点了名，但类还不存在

`RESTIR_REUSE_DEPTH` 的 javadoc 早就写着「RtRestirStats 报告每层深度的接受率」。这是回答「深层值不值 530 MB」的唯一依据，落地为 host-visible 计数缓冲。

- **计数不是标志位。** 一个像素的每条路径在每层深度上独立发问且经常给出不同答案，按位 OR 会让「任何一条路径接受」就记成整像素接受，报出来的率偏乐观——而那正是这一层深度被审判的那个数。用每深度一个 nibble 计数、饱和在 15。
- **抽样 1/16，随帧轮转。** 比值在抽样下无偏（分子分母同一批像素），代价从两百万次原子加降到十几万次。
- **不用 subgroup 归约。** 光追 stage 不保证在 `subgroupSupportedStages` 里；一个在某些驱动上编不过的诊断，比多发十六次原子加更糟。
- **某层深度「没有任何路径到达」不计作拒绝**，否则深层会因为一个完全无关的原因（根本没走那么深）被报成没用。

### 顺带堵掉的一个 32 位坑

`reservoirSlot` 返回 `uint`，反汇编生成的 SPIR-V 确认 `OpPtrAccessChain` 的 Element 就是 32 位。驱动是否在乘 64 B 步长前先扩宽，规范没有钉死。所以把 store 钉在 4 GiB 以下，让这个问题不可能发生——1080p / spp 1 恰好在顶格（深度 8 = 3.96 GiB）能塞下，1440p 或 spp 2 塞不下，两者都是设置界面里点得到的配置。超了就削深度并打日志。

**削减值必须参与 `ensureOutput` 的提前返回判定，而不是原始请求值**。否则条件永远不满足，那个最大 4 GB 的缓冲会每帧释放重建、每次还带一次 `waitIdle`——表现为帧率塌方而画面一个像素都不错。这是 D180 里那个「设置晚一次 resize 才生效」bug 的镜像版本。

### S1 是有偏的，而且知道偏在哪

存下的 reservoir 的 M 个候选是在**上一帧的顶点**上抽的，把它们当作这一帧这个顶点的候选来计数，就是不带 MIS 权重的朴素 ReSTIR 合并。两个顶点对光源看法不同的地方（轮廓、掠射角、26° 法线窗口放进来的一切）M 增长而权重没有，结果偏暗。接收端检查是让它保持小的东西，**S2 的 MIS 权重才是消除它的东西**。

故意没有加「存下的样本在这里没贡献就不计 M」这种补丁：它会把偏暗藏起来，换成一个讲不出道理的偏亮，还会让 S2 更难干净地替换掉这一项。

## D183：第一次实测，深层复用当场出局

首次游戏内运行（533×300 渲染分辨率，深度 4，`diagnostics.restir-stats` 开）：

| 深度 | 接受率 | 尝试数 |
| --- | --- | --- |
| d0（主命中） | 静止 **95–99%**；相机一动掉到 **0–30%** | ~9,994 |
| d1 | **0.0–0.7%** | ~9,700 |
| d2 | **0.0–0.1%** | ~9,400 |
| d3 | **0.0%** | 200–450（RR 早已终止路径） |

d0 尝试数 9,994 = 159,900 像素 ÷ 16，与抽样率精确吻合——统计本身的算术先自证了一遍。

### 深层不是调参问题，是机制问题

不能只凭「率很低」就宣称结论（`b5a558f` 的规矩），所以去核了机制。`world_primary.rgen.slang:323`：

```
seed = (pixel hash) ^ (worldPush.frameIndex * 2654435761u)
```

**弹射方向每帧独立重采样**。上一帧该像素的第 1 次弹射顶点与这一帧的，是两个独立余弦半球样本，通常隔着几米。0.05 格的位置检查不可能通过，**0.3% 就是两者偶然重合的概率**。d1 有 9,700 次尝试，说明代码路径确实在跑，率低不是没执行。

**放宽阈值救不了**：那只会变成把上一帧的光照贴到不同几何上，正是该检查存在的理由。

结论：**深度 >1 是纯废料**，1080p 下深度 4 里有 1.6 GB 属于此类。D180 的实验拿到了比预期更彻底的答案——不是「该不该压缩」，是「根本不该存」。

**旋钮不降上限**（用户裁定）：默认仍是 0，文档与 tooltip 改为「1 是唯一有用的档」。保留能力是因为 **S2 的空间复用可能救活 d1**——空间复用不要求顶点跨帧存在，只要求邻像素本帧的顶点相似，届时同一个统计可以直接重测。

### d0 的真问题：一动就失效

95–99% 只在站着不动时成立，因为槽位按**原始像素下标**寻址、没有任何重投影。而这是最糟的方向：噪声在运动时最刺眼，静止时最不明显——这个特性只在最不需要它的时候起作用。

修法用现成的东西：`prevViewProj`（jitter-free）+ `camDelta` 把命中点投影回上一帧屏幕，取那个像素的槽。`guides.slang` 早有同一份数学（`projectPrevNdc`，运动矢量就是这么算的），但 pass B **故意不 import guides**，所以把它移到两边都 import 的 `world_core`，一份定义。

三条设计要点：

1. **只有读被重投影，写永远落在本调用自己的像素上。** 写也跟着投影的话，两个像素投到同一处就会争抢一个槽，store 会出现空洞——而空洞看起来和低接受率一模一样。
2. **重投影错了只会漏掉复用，不会用错。** 落到错误像素 → 存下的接收端位置过不了漂移检查 → 拒绝。移动实体（本版不建模物体位移）和折射顶点因此自动退化，不需要额外分支。这个不对称是「近似重投影」可以安全的全部依据。
3. **只在主命中做。** 弹射顶点不在相机射线上，它投影到的那个像素是「主命中在那儿」的像素，那个像素的弹射顶点在别处。没有重投影可做——这与「深层不值得存」是两件独立的事。

**四舍五入而非向下取整**：本帧射线离像素中心最多半个像素的 jitter（`FluoriteJitter` 是 `halton - 0.5`），所以最近的像素就是投它的那个；向下取整会把静止相机一半的帧送给邻居。

### 已知未解：容差在远处会不够

即使重投影完全正确，上一帧那个像素打中的点与本帧这个点仍然差约半个像素的视差。533×300、70° FOV 下约 0.0023 rad/像素：10 格处半像素 ≈ 0.011 格（0.05 容差够），100 格处 ≈ 0.115 格（不够），掠射角还要再除以 cos。

**所以预期是近处救回来、远处和掠射面仍然拒绝。** 没有顺手把绝对位置判据改成平面距离判据——那是第二个方向性改动，而这次只改一件事，让统计自己说容差是不是下一个瓶颈。

## D184：偏差在哪、为什么时间那部分几乎修不出东西来

开工 S2a 时先把「S1 有偏」这句话推到底，结果比原先写的更精确。

朴素 ReSTIR 的权重是 `m_i = M_i/M`。**它们加起来确实等于 1，所以本身是合法的 MIS 权重** —— 偏差不来自「没做 MIS」，而来自 MIS 权重必须**在能产生该样本的域上**求和为 1。当某个光源落在另一个顶点的地平线以下，那个域的目标函数在该样本上是 0，它根本产生不了这个样本，却仍被计了 `M_prev/M` 的权 —— 总权重于是小于 1，**结果偏暗**。

替换成广义平衡启发式：

```
m_i(y) = M_i · phat_i(y) / Σ_j M_j · phat_j(y)
```

它在 `phat_i(y) = 0` 处恰好为零，因此永远只在能产生 y 的域上求和为 1。估计量随之变成 `W = wSum / phat(y)`，**分母里不再有 M** —— MIS 权重已经做完那次归一化，再除一次就是除两遍。

### 一个可预测的结果，正是先做它的理由

当两个域的目标函数相同时，`m_i` 退化为 `M_i/M`，整个式子**逐项等于旧式**。而时间复用的接收端校验只放行 0.05 格 / 26° 以内的顶点 —— 两个域的目标函数通常就是同一个函数。

**所以时间那部分的修正量预计几乎看不见，这不是失败而是先做它的原因**：机器在一个答案可预测的两域情形上验证过了，再拿去用在空间复用那个答案不可预测的情形上。退化性质本身写成了数值测试（`theMisWeightIsTheBalanceHeuristicAndReducesToTheOldFormWhenDomainsAgree`），跨 M 与 phat 的多组取值断言两式相等。

真正会变的是**地平线附近**：法线在 26° 窗口内转动、把光源从一侧翻到另一侧的那些像素。轮廓线和掠射面。

### 没有阴影线参与

目标函数是**无遮挡**贡献，可见性由 `shadeReservoir` 事后乘一次。RIS 对任何在被积函数支撑集上为正的目标都无偏，而无遮挡贡献在有遮挡贡献为正处必为正 —— 所以不需要 2020 论文那个「带可见性的无偏变体」的额外阴影线。

### 目标函数值存进最后一条 lane，但换了个名字

公式要三个目标值，其中「存下的样本在它自己那个顶点上的目标值」正是存的时候算过的。存进 `misc.w`，省一次求值且比重建更准（重建只能拿当前材质配存下的几何）。

**但 D181 明明说 phat 故意不存。**两者不矛盾，是两个不同的量：D181 警告的是把它当作**估计量的分母**（那必须在复用它的顶点上重算），这里用的是它作为**产生该样本那个域的 MIS 权重分子**。为了让人无法混用：`unpackReservoir` 仍然返回 `phat = 0`，存的那个值只通过另一个名字 `storedSourceTarget()` 暴露，命名按「哪个域」而不是按「哪个量」。测试断言 `unpackReservoir` 里不许出现 `storedSourceTarget`。

### 另一个域的材质取不到，只能近似

算 `phat_prev` 需要那个顶点的 BsdfContext，而我们只存了位置和法线。`retargetBsdfContext`（放在 `bsdf.slang` 的构造函数旁边，共用同一套派生表达式）拿**当前材质配存下的几何**，各向异性的纹理方向用 Gram-Schmidt 重新贴到新法线上（26° 下切线离新法线至少 64°，条件数没问题）。

时间复用上这几乎是精确的（同一个面，多半就是同一个材质）。**空间复用跨材质边界时会错，而误差落在 MIS 权重里而不是估计值里 —— 表现为方差而不是错误的画面。**

代价：每个复用顶点两次 `evalSampleContrib`（原来一次）。都在 d0，每顶点一次，不在 M=8 的候选循环里；而候选循环那 5.9 ms 的主因是 alias→grid→record 的追指针链，这里没有。

## D185：空间复用用成对 MIS，邻居读上一帧

四个方向性问题请示用户，四个都按推荐档定：邻居**读上一帧半区**、**拆成 S2a/S2b 两个 PR**、**空间用平面距离判据而时间维持原样**、MIS 用平衡启发式（这条我没问，理由见 D184）。

### 为什么不是完整的平衡启发式

k+1 个域的完整平衡启发式要 `phat_j(y_i)` 的全部配对，**k² 次目标函数求值**。改用**对着 canonical 的成对 MIS**：

```
p_i(y) = M_i phat_i(y) / (M_i phat_i(y) + M_c phat_c(y)),   q_i(y) = 1 - p_i(y)
m_i(y) = p_i(y) / k                    m_c(y) = (1/k) Σ_i q_i(y)
```

求和为 1 是构造出来的：`(1/k) Σ_i (p_i + q_i) = 1`。每个域**两次求值**，且 **k = 1 时逐项还原成 D184 那个两域平衡启发式** —— 所以 S2a 是 S2b 的 k=1 特例，不是被替换掉的旧版本。

`m_c` 是每次成对比较留给 canonical 的份额的**平均**，所以在所有域都提交完之前算不出来 → canonical **最后入流**，`qSum` 一路累加，`restirCombineFinish` 再除以 k。副作用：k=1 时随机数消耗顺序与 S2a 不同（两次抽样而非一次），分布相同但帧不逐位一致。旋钮的关档契约是 `RESTIR_REUSE_DEPTH = 0`，不受影响。

### 为什么读上一帧，以及它的代价

这个 dispatch 里**没有「所有 reservoir 都写完了但还没着色」的接缝** —— 着色内联在弹射循环里。读本帧邻居就是读它们碰巧执行到哪一步。上一帧半区按定义是完整的，而且让空间与时间**合成一个域循环**而不是两套机制。

代价：空间邻居也是一帧前的。

被否掉的另一条是把 d0 的 RIS 挪进 pass A 换取真正的同帧邻居 —— 那会把 `BsdfContext` 的构造分叉成两份，而 `world.rgen.slang:492` 的注释已经写明「重建三次正是它们悄悄不一致的原因」。

### 一个必须说清的推论：读上一帧，空间救不了 d1

保留深度旋钮的理由是「空间复用不要求顶点跨帧存在」。**在这个实现里那句话不成立**：邻居像素在**上一帧**的 d1 顶点，同样是一次独立的半球采样，和本像素上一帧的 d1 顶点统计上没有区别。

所以真正可能改变 d1 的**不是「空间」，是「判据」**。D183 测到的 0.3% 其实测的是 **0.05 格绝对位置判据**，不是复用机会本身——两个落在同一面墙上、相距两米的顶点，绝对位置判据必拒，平面距离判据可能过。这一版让统计**分开报告时间/空间两个接受率**（`d0=t95.0%(9994)/s40.0%(2000)`），就是为了让这件事能被看见而不是被推断。

### 判据与常数

空间判据三项：**离面距离** ≤ 0.05 格（拒绝身后/身前的另一个面）、法线夹角（与时间共用）、**侧向距离上限**——没有它，一大片平地上任意两个像素都能互相复用，那不再是邻域复用而是整个平面复用。

侧向上限以**像素足迹**为单位而不是格：固定距离在远处只覆盖不到一个像素、在脚下覆盖十几个。`surfaceFootprint(coneWidth, rd, n)` 提到 `world_core`，雨涟漪原本就在算同一个量，现在共用一份定义。

`RESTIR_SPATIAL_RADIUS_PIXELS = 12`、`REUSE_LATERAL_FOOTPRINTS = 24` 都**未校准**（§8.11）。两者从两端夹：搜索半径太小则邻居冗余，太大则读进来就被拒——只有接受率能说是哪一边。圆盘采样取 `sqrt(rnd)` 半径而非均匀半径，否则样本堆在中心，而中心最可能就是已经读过的那个像素。

### 关档

`composite.restir-spatial-neighbours` 默认 **0**：循环一次都不进，估计量就是 D184 测量时的那个。**不占任何显存** —— 邻居读的是复用深度已经分配的槽位。深度为 0 时整个特性不启用。

## D187：S3 上半场——动态光源接进候选集

`RtEntities.java:1716` 从 M18 起就写着「collection is measurable now, sampling waits for ReSTIR」。现在接上了。

四个方向性问题请示用户，三个按推荐档定，第三个把里程碑拆开了。

### 提议通道：第三条分层，而不是并入 alias 表

动态光在**自己的每帧缓冲**里，而 alias 表和密集光网格是**随地形增量构建**的 —— 要让实体进去，两者都得每帧全量重建。所以从 M 个候选里**预留一部分**给动态缓冲，是让它们被提议出来而又不动那两个结构的唯一便宜办法。

代价说清楚：**这个份额是固定的，不按功率加权。** 一屋子火把和一个举火把的生物拿到同样多的候选。并入 alias 表才能按发光功率自动分配，那是下一步的明显改良，且不免费。

**两个缓冲的形状不相交**（那边全是矩形，这边全是球），于是三路混合密度是平凡的：没有候选能被一个以上的通道提议，每个候选的 pdf 就是它自己那条通道的项，不用跨通道求和。

**预留发生在 local/global 划分之前**，剩下的照原样分。而且**两条通道的密度都要按各自份额缩放** —— 混合是对全部 M 个候选定义的，扣掉一部分就改变了每条密度描述的比例。漏掉这一步会让静态光的权重按「交给实体的那一份」等比虚高，表现为一个跟着旋钮走的整体变亮，而看起来像是实体变亮了。

上限卡在 `candidateCount - 1`：一个顶点不能把全部预算花在实体上，然后看不见它所站的世界。

### 球采样：面向接收点的半球，按面积

整球采样会把一半候选扔在背面（发光体余弦归零），而候选循环正是实测 5.9 ms 的热路径。半球一个不浪费，且**不需要第二条 pdf 路径** —— 在 2πr² 上均匀、密度 1/(2πr²)，正是 `evalSampleContrib` 的 `area` 参数表达的契约。

`z` 在 [0,1] 均匀是让它**按面积**均匀而不是往极点堆积的那一步（球带等面积恒等式）。

**它是精确的，更宽的采样域花掉的是样本而不是准确度。**（我第一版注释把这里写成了「轻微偏亮」，自查时算错了，已改。）

从距离 D 的一点实际可见的是 `dot(n, d) > r` 的冠，确实比半球小。但两者之间那条带**不需要额外的测试**：对 `x = c + r·n`，`evalSampleContrib` 的发光体余弦项正比于 `dot(n, d) − r` —— **正是那个冠的定义式**。所以轮廓带的贡献恰好为零，没有任何多算；采样它只是浪费掉 `r/D` 比例的动态候选。

蒙特卡洛验证过（`z` 均匀时带占比 0.3345 对预测 r/D = 0.3333，保留占比 0.6655 对 1 − r/D）。实体、手持火把、火焰粒子的半径都很小，浪费可忽略；只有接收点几乎贴着发光体时才显著。接收点落在球内则整体拒绝。

### 两个静默失败点，各配一个测试

**一、坐标约定。** 静态缓冲的位置在地形层级空间、出口处加 `lightRebase`；动态缓冲**每帧从活实体重建，本来就在当前 rebase 空间**。多加一次偏移能编译、能跑，把每个实体的光放到一个 rebase 距离之外 —— 远到看起来像「动态光不工作」而不像一个偏移。

**二、索引归属。** 有了两个缓冲，索引 7 在两边指不同的光。光源身份校验存在的意义就是抓住「这个 reservoir 的光已经不是它来的那个光」，而不带缓冲标记就会去读错的缓冲、跟一个不相干的发光体比对 —— 多数时候拒绝，**偶尔接受**，正好把那个检查要防的失败原样放回来。`lightIndex` 的 bit31 做标记（两个缓冲都不会有二十亿条记录），`RESERVOIR_NO_LIGHT` 因为其余位全 1 而与任何带标记的索引区分得开。

球的身份校验与矩形同构：radiance、面积（经由 `2πr²` 反推半径）、以及「存下的点是否仍在球面上」—— 最后这一项是**移动过的光唯一过不了的那个**。

### 关档是逐位的

`dynamicRisCandidates = 0` 时 `staticCandidateCount == candidateCount`，划分与旧版一致，静态密度乘以 `1.0`（IEEE 下精确无变化），且动态分支一次都不进、**不消耗任何随机数**。缓冲为空时通道整体跳过，发布端也不发布旋钮 —— 否则会预留候选再扔掉，读起来像「RIS 变差了」而不是「这个设置没生效」。

### `UNWEIGHTED_SPEC_ALPHA_FLOOR` 拆出去了

§8.9 原本把它和动态光写在同一行。两者**没有共同代码**：移除高光下限需要让 BSDF 光线打中发光体时也计数并做 MIS 加权，而 MIS 要另一个策略在该方向的 pdf —— 那个策略是 **RIS 重采样，它的 pdf 没有解析形式**。文献里有做法，没有干净答案，全是近似。

捆在一起做，出问题时分不清是哪一半，而且高光那一半会同时改变静态光的画面，与动态光接入的效果叠在一起看。用户裁定拆开。

### 根因

灯笼是少数**拥有专属 item 贴图**的发光方块。火把的物品模型指向 `block/torch`、萤石指向方块模型，都落在方块图集；灯笼指向 `item/lantern`，落在**物品图集**。而材质编译只扫描方块图集，物品精灵因此没有任何材质，解析落到用 `EmissionSummary.NONE` 编译的 fallback。

所以**单放宽闸门没用**——拒绝点只会从第一道挪到第二道。三处必须同时改，且各自失败都是静默的：编译要**看见**这些精灵、发射语义要**许可**它们、手持光观察器要**接受**它们。

### 裁定与一次修正后的重新请示

先给了两个选项：回退到方块自己的精灵（~15 行），或把物品图集编进材质表。用户选了后者。

**动手后发现我低估了它**：`RtEmissionSemantics` 只遍历方块状态→方块模型，物品精灵没有第二条发现途径——按名字匹配被项目规矩明令禁止（而且对「只重贴图物品不重贴图方块」的资源包本来就是错的）。真正要做的是**新写一遍物品模型解析**（`ItemModelResolver.updateForTopItem` → `ItemStackRenderState` 的层 → `BakedQuad` 的精灵），而 `layers` 与 `quads` 都是私有的，**还要两个新 mixin accessor**。

带着修正后的代价重新请示，用户维持根治。

### 实现要点

- 用 `ItemDisplayContext.GROUND` 解析：display context 只选**变换**，与模型用哪些精灵无关，而手部上下文会把手臂模型一起拖进来。
- 读 `quads` 字段而不是调 `prepareQuadList()`——后者是给写入方返回一个**空表**去填的，用它来读会把要问的东西清掉。测试专门断言了这一点。
- 扫描 ≠ 编译：精灵仍需凭 `_s`/`_n` 兄弟文件或「出现在发光物上」的证明才拿到材质，所以普通物品只多一次 map 查询，下游零成本。

## D189：发光体亮度与色温，以及一个会让旋钮精确失效的陷阱

用户要求给这些光源加亮度与色温调节。两个方向性问题请示后定案：**作用于所有发光体**（而非只动态光，否则手里的火把和墙上的同一个火把会不一样亮）、**黑体色温且保亮度**。

### 陷阱：在解码处染色，滑块会精确地什么都不做

第一直觉是在 `lightRadiance()`（静态与动态两个缓冲共用的解码）里乘上倍率。**那样滑块拉满也不会动一个像素。**

`proposalPdf` 用 `power = area × luminance(le)` 重算功率，而归一化用的 `lightRebase.w`（总功率倒数）是 CPU 侧未染色发布的。于是：

- `p` 整体乘以 `brightness`
- `phat` 也乘以 `brightness`
- `wSum = Σ phat_i/p_i` **不变**
- `W = wSum/(M·phat)` 除以 `brightness`
- 估计量 `f·W` = `brightness × (1/brightness)` = **1**

体积路径同理：`sampleVolumeEmitter` 把 `sample.radiance` 同时交给了 `emitterProposalPdf`。

**正确的位置是「radiance 变成出射光」的那一刻**，不是解码的那一刻。染色处：`evalSampleContrib` 顶部（覆盖 RIS 目标函数与两个 contrib 分支）、`shadeReservoir` 里直接吃 `s.le` 的 Disney 项、`volumeNee` 的 contrib、以及 `world.rgen.slang` 的直击自发光。

**不染色处**：任何解码、任何提议密度、以及 **ReSTIR 存储**。存储必须保持原始 radiance —— 光源身份校验拿存下的 `leW` 和重读的记录比对，只染一侧会让每个存下的样本都被拒。

这两个方向的失败都是静默的，所以都写成了测试而不是注释。

### 色温：保亮度是让两个旋钮正交的那一步

Kim 等人的普朗克轨迹三次拟合给出 CIE 1931 xy → XYZ（Y=1）→ 线性 sRGB → **除以自身的 Rec.709 亮度**。于是色温只改颜色、绝不改亮度，亮度滑块因此是唯一回答「这屋子是不是太暗」的东西。若 tint 自带亮度，每次调色温都同时是一次调亮度，两个旋钮永远校不准。

2000K 以下的色度落在 sRGB 色域外，负通道钳到 0 —— 颜色因此落在色域边界上而不是变成另一个颜色，且**归一化在钳位之后**，所以钳位损失的是饱和度不是亮度。

**它同样作用于本来不是白炽体的发光物**（萤石、海晶灯没有温度），那是艺术选择而非物理，所以默认关闭而不是给一个「看起来合理的火焰值」。

### 关档

亮度 1 = 乘一（IEEE 精确不变），色温 0 = 完全跳过轨迹计算。两者都关时与已发布画面**逐位一致**。

### 放在 WorldPush 而不是材质表

`emissionStrength()` 才是静态方块光、动态球光、发光表面外观三者真正共用的因子——但它在**材质编译期**，改它要重编材质表。一个必须重编材质才生效的滑块没法边看边调，所以改在着色器侧的四个消费点，每帧发布一个 `float4 emitterTint`。

## D190：逐材质色温——以及为什么色温可以烘焙而亮度不能

用户表示接下来要「进入文件里面仔细调整每个发光体的强度和色温」。查了 `RtMaterialOverrides` 的实际能力：**强度已经可以**（`emission.strength`，0–5 的逐材质倍率），**色温做不到** —— 那个格式里唯一沾颜色的字段是 `emission.color_source`，且只接受 `"albedo"`，写别的直接抛异常。

而这个用法恰恰需要逐个：火把 1800K、灯笼 2000K、萤石根本不是白炽体（该保留自己的颜色）。全局旋钮给不了三个不同的值。

### 关键发现：色温和亮度的对称性是假的

D189 把亮度按在着色点上，是因为放在解码处会被提议密度精确抵消。**色温没有这个问题** —— tint 的亮度恒为 1，`proposalPdf` 的 `luminance(le)` 完全不受影响。

所以色温可以安全地在**采集期烘焙进光源记录**，而亮度不行。这一条不对称把逐材质色温的成本从「一路带标志到四个着色点 + Reservoir 多带一位 + 存储跟着改」降成了「在编译期改一次 `EmissionSummary` 的平均色」。

代价：全局色温滑块从实时变成重载生效。请示后用户接受——他本来就要在文件里调，那本来就要 F3+T。**亮度滑块仍然实时。**

### 实现落点：`EmissionSummary` 的平均色

`EmissionSummary` 的 `averageRGB` 是两个光源采集器（静态矩形与动态球）**共同的**辐射度来源。在编译期重新着色它，下游全部路径零改动地继承 —— 方块光、实体/手持球光、粒子簇。

`integratedLuminance` 与 `coverage` **不动**，且按构造仍然正确，因为 tint 的亮度是 1。这也正是提议密度对这一切毫无察觉的原因。

### 三个容易搞反的点，各配一个测试

**一、覆盖而非相乘。** `emission.strength` 是乘法，色温是替换 —— **两个色温相乘不是色温**，一个物体只有一个温度。

**二、必须在 override 之后施加。** 第一版写在 `variantSummary`（每个编译材质的发射色都经过的漏斗）里，那是**错的**：资源包授权的温度会去给一个已经被重新着色过的颜色再着一次色，得到的不是要的那个颜色。改为 `withEmitterTemperature(rule.apply(desc), rule.emissionTemperatureK())`，包在每一个 `rule.apply` 外面——测试用计数断言「每个 apply 都被包住」，漏一个就红。

**三、授权的 0 不是「未授权」。** 这是最容易合并掉的一个：`temperature_k: 0` 的意思是**「保留我自己的颜色」**，这是萤石、海晶灯这类根本不是白炽体的发光物对抗全局设置的唯一方式；而**省略该键**才是「继承全局」。把两者合并，这些发光体就会被全局滑块拖着走且没有出路。因此 `tint()` 收一个显式的 `authored` 布尔，而不是靠 `kelvin > 0` 推断。

### 已知的不一致

烘焙只作用于**光源记录**，即发光体投出去的光。发光**表面自身的外观**仍然是贴图颜色 × 标量 emission，不受色温影响 —— 所以一个授权成 1800K 的火把会投出暖光，而它自己看起来不变。

这未必是错的（火把贴图本来就是橙的，再叠一层黑体等于加倍变暖），但它是个不一致，记在这里而不是藏起来。

### 两条测试自己先没抓住东西

变异验证时两条测试是绿的，都是测试的毛病而不是代码的：

**「授权的 0」那条**，因为全局色温**默认就是 0** —— 于是「授权 0」和「继承全局」在测试环境下恰好同值，把 `authored` 布尔换成 `kelvin > 0` 推断也照样绿。修法是在测试里把全局设成 6500K 再断言，两个读法才分得开。**默认值与被测语义重合，是断言失效的一类常见死角。**

**范围检查那条**，因为它断言的是**源码文本**。变异只删掉了 NaN/负数检查、留下范围检查，它要找的那段文字属于活下来的那一半，于是绿。改成走 `RtMaterialOverrides.parse` 的**行为测试**：喂 999 / 12001 / -1 / NaN 断言抛出，喂 1800 / 0 断言通过，省略该键断言返回 null。改完后三种拆法（删 NaN 检查、删范围检查、把省略当成 0）全部变红。

## D193 两条裁决（用户，2026-08-19）

**复用域：世界空间哈希网格。** 另外两条被否：

| 域 | 否掉的理由 |
| --- | --- |
| froxel 锚定 | 显存几乎为零、基建现成，但**视锥体绑定**——反射里的雾没有 froxel 可查，而 R18 明写云代码里不得出现相机位置，体积照明是同一条原则的延伸。选它等于把「反射里成立」推给下一个里程碑。 |
| 逐像素逐段 | 与 M24 同构、代码可复用，但显存与表面 store 同量级。**用户三天前刚因 2812 MiB 的表面 store 崩过一次**（1600×900 × depth 2 × 8 paths），再叠一份同量级的存储不是可接受的起点。 |

世界空间的代价写在明处：**全新数据结构 + 淘汰策略，而淘汰策略错了会以「闪烁」而不是报错的形式表现。**

它换来的三件事：按需分配（显存随实际被照亮的体积走，不随分辨率走）、跨视角跨弹射复用、以及**时间复用不需要重投影**——一个世界空间格子本来就不动，而 M24 的 d0 重投影花了一整个 D181 才把接受率从双峰做成连续。

**首切范围：只做天空可见性。** 直接打 Issue #41（洞穴远场雾被无遮挡天空照亮），不动现有的发光体 `volumeNee`。理由是它能单独验证：洞穴里天空可见性应当是 0，而现在不是。

## 待裁决（开工前）

1. **哈希键的 LOD 策略。** 格子尺寸随距相机距离增长（`level = log2(dist × k)`），否则远场格子数会爆。但 k 决定了远场的质量上限，而 #41 的症状正在远场。
2. **淘汰策略。** 开放寻址 + 每格帧戳 + N 帧未触碰即回收。N 太小则复用断裂（噪声），太大则显存涨且陈旧样本残留（拖影）。**这两个失败方向都表现为画面问题而不是错误。**
3. **与现有可见性网格的关系。** 现有雾读的是一张缓存可见性网格（§2.8 的第三层近似）。新旧两条路必须要么 MIS、要么分区，且**铁律 8：关档必须等于已发布行为**。
4. **目标函数。** 天空可见性的 `phat` 至少含天空辐亮度 × 相位；是否含透射率影响时间复用的有效性。
